## Blocking bridge answer lost under load (#298)

- Landed: `PendingReply::wait(None)` and `Client::send(..., None)` no longer call `set_read_timeout(None)` / `set_write_timeout(None)`. A fresh socket is already blocking with no timeout. Added a regression test that reads a reply after the island has closed its end.
- Where: `shared/crates/morrow-ipc/src/unix/client.rs`, `shared/crates/morrow-ipc/tests/unix_socket.rs`.
- Verified: the new test fails with `EINVAL` on the old code and passes with the fix; 12 repeated runs of `unix_socket` and `bridge_process` all green; 400 gemini fixture runs under CPU-busy workers went from 1 to 3 failures per 240-400 before the fix to 0 after.
- Left open: none. The reported full-workspace failures were not deadline expiry: failing runs ended in 0.3 s, and the bridge logged `set read timeout on …: Invalid argument (os error 22)`.
- Why: macOS refuses `setsockopt(SO_RCVTIMEO, 0)` once the peer has closed. Gemini's island answers and drops the connection at once, so under load the peer often closed before the bridge set the timeout. Treating that syscall error as fatal dropped the already-buffered answer, so the hook printed nothing.
